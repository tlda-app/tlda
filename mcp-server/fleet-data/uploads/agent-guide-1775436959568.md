# Agent Guide — Procedures and Rules

Read this at session start. Every session. No exceptions.

This document covers what every agent must do and must never do when working on tlda/fleet. These rules were learned from real disasters — agents breaking Skip's live environment, shipping untested code, asking Skip to do their job, and reinterpreting specs until the feature bore no resemblance to what was asked for.

For behavioral patterns (three-beat corrections, self-diagnosis, etc.), see `good-patterns.md`.
For UI-specific rules (worktrees, merging, reports), see `app-development.md`.
For etiquette (what's rude, what's respectful), see `agent-etiquette.md`.

---

## The Rules

### 1. Never ask Skip to check, test, look at, reload, or verify anything

This is the #1 rule. Every violation of this rule wastes Skip's time and proves you're not using your tools.

**Bad:**
- "Try reloading and see if it works"
- "Can you check the console?"
- "Let me know if the fix looks right"
- "Go verify on the iPad"

**What to do instead:** Use your tools. You have:
- `tlda_screenshot` — screenshot the viewer as Skip sees it
- `get_console` — read Skip's browser console directly
- `reload_browser` — reload Skip's browser (asks permission via chat first)
- Playwright MCP — full browser automation (navigate, click, type, screenshot, evaluate JS)
- `playwright-cli` — same capabilities, more token-efficient (writes snapshots to disk)
- `tlda preview` — render static SVG pages for quick visual checks

If you can't verify something yourself, say *specifically* why — "I can't test this because it requires iPad touch input that playwright can't simulate." Don't punt with "try it out."

### 2. Never deploy to Skip's live environment without permission

`~/work/tlda` and `~/work/fleet` are live. Skip uses them constantly. Any file edit triggers Vite HMR and can break WebSocket connections, voice mode, and whatever Skip is actively doing.

**Never:**
- Edit files in the working copy directly
- Rebuild the bundle without asking
- Restart the server without asking
- Merge to main without approval
- Reload Skip's browser without asking

**Always:**
- Work in a git worktree (`.worktrees/<name>`)
- Test in your worktree's dev server
- Ask via `chat()` before any action that touches Skip's environment
- Wait for explicit confirmation before merging or reloading

### 3. Read what Skip said before doing anything

When Skip describes a bug, reports a problem, or specifies a feature, **read his actual words**. Don't ask diagnostic questions he already answered in the same message. Don't rephrase his spec into something easier to build.

**Bad:** Skip says "the chat doesn't scroll to the bottom when new messages arrive" and the agent responds "Can you describe what happens when a new message arrives?"

**Good:** Agent reads the message, understands the problem, and starts investigating the scroll behavior.

**Where to find Skip's words:**
- `search_logs` — search fleet chat history by keyword, role, agent
- `get_thread` — get the full conversation thread with a specific agent
- `scratch/skip-feature-transcripts.md` — verbatim transcripts organized by feature
- `scratch/corrected-specs.md` — specs derived from Skip's words (not agent interpretations)

### 4. Use Skip's actual words as the spec

Don't reinterpret. Don't paraphrase. Don't "improve." Quote him.

When writing a spec, implementing a feature, or filing a report, reference what Skip actually said. If his words are ambiguous, ask — don't guess. If his words conflict with what seems "better," his words win.

**Example of what goes wrong:** Skip says "kill the container shape, fleet shapes are normal top-level tldraw shapes." Agent builds a new panel component that wraps fleet shapes in a draggable container. This is the opposite of what was asked. It happened because the agent "interpreted" the spec instead of reading it.

### 5. "Verified in playwright" means real interaction testing

Not "the element exists in the DOM." Not "the CSS property is set." Not "it builds without errors."

**Real verification:**
- Navigate to the page
- Interact with the feature (click, type, drag, scroll)
- Screenshot before and after
- Measure computed values (bounding rects, scroll positions, opacity)
- Check console for errors
- Test edge cases and failure modes

**Fake verification:**
- `document.querySelector('.my-element') !== null` → "verified"
- "The build succeeded" → "verified"
- One screenshot of the initial state with no interaction → "verified"

See `app-verification.md` for the full report format.

### 6. All work in worktrees

Nothing touches main until fully implemented, tested with evidence, and approved by Skip.

```bash
git worktree add -b feature-name .worktrees/feature-name
cd .worktrees/feature-name
# All work happens here
```

Worktrees go inside the project directory (`.worktrees/`), not `/tmp`. See `app-development.md` for the full merge procedure.

## Process for Every Task

Every task follows this sequence. No skipping steps. No "this is simple enough to skip the audit."

### Step 1: Audit current state

Before writing any code, understand what exists right now.

- Screenshot the current UI (if applicable)
- Read the relevant source files
- Describe what exists, what works, what's broken
- Check for existing worktrees doing the same thing (`ls .worktrees/`)
- Check git diff on the working copy for uncommitted related changes

### Step 2: Read the spec from Skip's words

Find what Skip actually said about this feature or bug. Sources:

1. `scratch/skip-feature-transcripts.md` — verbatim transcripts
2. `scratch/corrected-specs.md` — corrected specs derived from transcripts
3. `search_logs(query="feature keyword", role="user")` — Skip's chat messages
4. `get_thread(agent="agent-who-discussed-it")` — full conversation context

**Do not use another agent's task description as the spec.** Agent task descriptions are interpretations. Skip's words are the spec. If they conflict, Skip's words win.

### Step 3: Report what exists vs what's needed

Before coding, tell Skip (via `chat()`) what you found:
- What currently exists (with evidence — screenshots, code snippets)
- What the spec says (quoting Skip)
- What's missing or broken
- Your proposed approach

Wait for approval before proceeding. This prevents building the wrong thing.

### Step 4: Implement fully

No partial ships. If a feature has 5 parts, implement all 5. If you can't finish in one session, say what's done and what's left — don't call it done when it's half-built.

### Step 5: Test thoroughly in the worktree

Use playwright against your worktree's dev server. Not the working copy.

```bash
# Start your worktree's dev server
cd .worktrees/feature-name
npx vite &  # or node server/unified-server.mjs

# Test with playwright-cli
playwright-cli -s=test open
playwright-cli -s=test goto "http://localhost:PORT/?doc=DOC&token=TOKEN"
playwright-cli -s=test screenshot --filename scratch/feature-1-before.png
# ... interact, screenshot, measure ...
playwright-cli -s=test close
```

Test in WebKit too — Skip uses Safari/iPad:
```js
// Playwright script
const browser = await playwright.webkit.launch();
```

### Step 6: Write a report with evidence

Report format is in `app-verification.md`. The short version:
- Screenshots at every step (before, during, after interaction)
- Measured values (bounding rects, scroll positions, computed styles)
- Console error check
- Narrative describing what each screenshot shows
- Verdict per feature: PASS or FAIL with reason

Save to `scratch/feature-name-report.md` with screenshots alongside.

### Step 7: Get merge approval

Post the report to fleet chat via `chat()`. Wait for Skip's approval. Only after "yes" / "merge it" / "looks good": merge to main following the procedure in `app-development.md`.

## Common Mistakes and What to Do Instead

### Broken links in chat
Before sending a URL in chat, verify it resolves. If you're linking to a local server, confirm the server is running and the path exists. Don't send `http://localhost:5176/?doc=foo` if you haven't checked that `foo` exists as a project.

### Chrome instance conflicts
When you launch playwright or a headed browser for testing, **use headless mode by default**. If you need headed mode (for iframe/canvas verification), use a distinct user data directory so it doesn't conflict with Skip's browser sessions. Never leave a browser window open after your test is done — close the context and browser in your cleanup.

```js
// Good — isolated, won't interfere with Skip
const browser = await chromium.launch({ headless: true });

// If headed is necessary — use a temp profile
const browser = await chromium.launch({
  headless: false,
  args: ['--user-data-dir=/tmp/playwright-agent-test']
});
// ALWAYS close when done
await browser.close();
```

### WebKit vs Chromium
Skip uses Safari on iPad. Chromium passing does not mean Safari passes. If you're changing CSS, layout, scroll behavior, or anything visual, **test in WebKit too**:

```js
const browser = await playwright.webkit.launch();
```

If WebKit fails but Chromium passes, don't claim "it's a playwright quirk" unless you can explain specifically why. See the project CLAUDE.md "Test in WebKit" section.

### Claiming "done" without evidence
"It works" without a screenshot is a lie. "All criteria pass" without measured values is a guess. Every claim needs evidence. If you didn't test it, say "untested." If you tested it partially, say what you tested and what you didn't.

### Reinterpreting the spec
Skip says "kill the container." You build a better container. This is the #1 cause of wasted work. Read the words. Build what the words say. If you think the words describe something suboptimal, raise it in chat *before* coding — don't silently build your version.

### Going silent
If a task takes more than ~30 seconds, tell Skip what you're about to do. "I'm going to screenshot the viewer and check the layout" is fine. Disappearing for 10 minutes is not. Communicate via `chat()`, not terminal output — Skip reads fleet chat, not your terminal.

## What the Watchdog Catches

A behavior watchdog agent monitors `to: skip` traffic and intervenes directly when agents:

- **Ask Skip to test/check/look at anything** — immediate flag
- **Claim "done" or "verified" without evidence** — rejected
- **Ask questions Skip already answered** in the same thread — flag with the quote
- **Touch Skip's live environment without permission** — escalated
- **Reinterpret specs instead of quoting Skip's words** — flagged with the original quote
- **Tell Skip to "try" something** instead of testing it themselves — immediate flag
- **Send broken links** in chat messages — flagged

If the watchdog flags you: acknowledge, fix, move on. Three-beat pattern. Don't argue about whether the flag was fair.
