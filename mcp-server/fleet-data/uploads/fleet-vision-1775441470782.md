# Fleet/tlda Vision

What this system is for, where it's going, and what to build next.

---

## The Core Thesis

The old dockview dashboard was a capable control panel — agents table, multi-chat, playback, search, terminal, tasks — but it was a separate app. It lived at a different port, didn't know about the canvas, didn't know about the document being reviewed. The fleet UI and the document viewer were two separate windows, with separate coordinate systems, separate state, and a loose coupling via HTTP.

The move to tldraw shapes is not just a technology swap. It's a different model: **the canvas is the workspace**. Fleet shapes (chat, agents, cluster, playback) are objects in the same space as document pages, annotations, math notes, and figures. You can zoom in on a conversation, place a chat panel next to the section it's about, drag a highlight from the document into a fleet chat. That spatial relationship is the point.

What hasn't been fully internalized yet is what that unlocks and what it demands.

---

## Where Things Stand

**Solid foundation:**
- FleetChatShape is feature-complete (filter, label drag, Esc interrupts, chip rendering, file upload, inline docs)
- FleetAgentsShape covers the core (team grouping, spawn/respawn, unread dots)
- ClusterShape (SLURM monitor) is done and merged
- HUD + group-transform layout overlay (W7) is done
- The chip system (W4/W5) has the right architecture, mostly landed

**In progress, nearly done:**
- PlaybackFrameShape on `w3a-playback` — the core play/pause/scrub is working; timewarp graph and curated layout mode are the remaining pieces before merge
- TerminalShape (W3c) — not yet on any identified branch, still spec

**Never built:**
- TasksShape — the tasks view from the old dashboard has no tldraw equivalent
- Settings/preferences in tlda
- Approval prompt detection + surfacing in fleet chat
- Agent-push layout (agents configure the HUD via MCP)
- Fleet+tlda playback recording (capturing the canvas state, not just fleet events)

## The 5 Most Important Things to Build

### 1. Merge PlaybackFrame (W3a)

**Why first:** It's nearly done on a branch, and playback is the highest-leverage feature — it's the only way to review what happened during a long agent session without sitting at the terminal. The timewarp graph (colored speed regions on the scrubber canvas) and curated layout mode (director's cut via layout keyframes) are the outstanding pieces. Both have precedent in the old `playback.mjs`. The design is clear.

**What done looks like:** `w3a-playback` merged to main. Recording picker works. Scrubber has timewarp visualization. `+HUD` populates inner fleet shapes. Curated mode applies layout keyframes from recording edits.

**Why it matters for the vision:** Playback is what makes the system coherent for async review. A manager who wasn't watching live can scrub through what happened, with the same chat/agents shapes they use for live monitoring — spatially arranged in the same canvas as the document they care about.

---

### 2. TasksShape

**Why:** The tasks view was in the old dashboard (`tasks.mjs`, 284 lines) and had features that don't exist anywhere in tlda: a filterable, sortable task table with status badges, delegated_by display, age, and success criteria count. Currently there is no way to see the task table in the tldraw workspace. The `fleet task_list` MCP tool exists but requires going to terminal or reading the agents panel (which shows current task inline but doesn't show the full list).

**What done looks like:** A `FleetTasksShape` — a placeable shape showing the task table with at minimum: agent pill, description, status badge, delegated_by, age. Sortable by status and age. Filter select (active/all/done/blocked). Click row → filters the selected FleetChatShape to that agent. Can be small (300×400px default).

**Why it matters for the vision:** Task visibility is the core of managing a fleet. The old dashboard had it; the new one doesn't. A manager sitting at the canvas should be able to glance at the task table alongside the chat and agents panels without switching views.

---

### 3. Approval Prompt Surfacing + TerminalShape (W3c)

**Why together:** These are two sides of the same problem. Agents get stuck waiting for approval prompts (CC permission dialogs, shell confirmations). Currently the only signal is silence — the agent stops responding. The fleet server already detects thinking/compacting states via the heartbeat poller; terminal-blocked is the same detection pathway with a different event type. When detected, the server should push a terminal card to the user (not the agent) so the prompt can be responded to from fleet chat without going to the terminal.

**What done looks like:**
- Fleet server: new `terminal-blocked` event type when agent's tmux pane shows an approval prompt pattern. Existing `terminal-state.mjs` + heartbeat poller handles detection.
- `TerminalShape`: xterm.js instance wired to `/api/terminal-state` SSE, with a send-key input. Opens automatically on `terminal-blocked` event, or can be placed manually from the toolbar.
- The terminal card is the fallback; Esc interrupts (W6, already done) handle the common case.

**Why it matters:** This closes the last case where going to the terminal is unavoidable. After this, the fleet chat is a complete agent interaction surface.

---

### 4. Canvas State in Fleet Recordings (Task #7)

**Why:** Right now fleet recordings capture what agents said and did (chat messages, tool calls, activity events). They don't capture what the canvas looked like. A "replay" of a session that included canvas annotations — highlights, math notes, document pages opened — loses all of that context. The playback reconstruction is hollow: you see the text conversation but not the spatial context it was embedded in.

**What done looks like:** The fleet recording system captures tldraw canvas snapshots at configurable intervals (e.g., every 10s during active sessions, on-demand via MCP). During playback, the PlaybackFrame applies canvas state snapshots as keyframe events — the same mechanism as curated layout mode. The shapes inside the frame reflect both the fleet conversation state and the canvas state at each point in time.

**Why it matters for the vision:** This is what makes playback a genuine time-machine for the whole workspace, not just the chat log. It also sets up the agent-push layout feature (task #8) — if agents can push canvas state in recordings, they can also push it live.

---

### 5. Agent-Push Layout (Task #8)

**Why:** The current model is: Skip arranges fleet shapes on the canvas manually. Agent-push layout inverts this — agents configure Skip's viewing layout via MCP, placing shapes, routing chat to the right panels, suggesting layouts for their current context. This is the full expression of the spatial model: the agent can say "I'm working on the bregman paper, here's the relevant section, here's the conversation about it" and Skip's canvas reflects that.

**What done looks like:**
- New MCP tools: `tlda_create_shape` (already partially exists), `tlda_arrange_layout` (arrange fleet shapes into a named layout), `tlda_push_layout` (push a layout to Skip's canvas).
- FleetHUD: shows a "proposed layout" indicator when an agent has pushed a layout. Skip can accept or dismiss.
- The fleet recording system (task #7) captures what was pushed.

**Why it matters:** This is the step from "Skip watches agents" to "agents collaborate with Skip spatially." It's what makes the canvas a shared workspace rather than Skip's personal view of a broadcast.

## Secondary Things Worth Doing

These matter but are lower priority or naturally follow from the above.

**roll_call enhancement** (`scratch/roll-call-enhancement-spec.md`): Add current task + status + idle flag + unread count to roll_call output. Pure server-side, no UI needed. Three round-trips reduced to one. This is the manager's most-used tool and it's underpowered.

**Resizable front-of-canvas panels**: RefViewer, BuildErrorOverlay, ProofStatementOverlay are fixed overlays. They should be HUD-style draggable/resizable panels. The CanvasClipPanel + FleetHUD architecture already demonstrates how to do this.

**Per-user layout persistence**: The tldraw canvas already persists shape positions (IndexedDB). But there's no concept of saving a named layout arrangement ("fleet: morning review mode" vs "fleet: deep work mode"). Low complexity to add, high daily value.

**Diff highlights via shadow repo**: Shadow repo is implemented (DocVersionShape, doc_version MCP tools). The next step is programmatic word-level change highlights on the viewer using the shadow repo diff. This closes the "unread changes" problem from the ISSUES file — agent makes a change, it glows briefly in the viewer.

---

## What Not to Build

**CodeMirror input**: The old dashboard used a full CodeMirror editor in the chat input (~25k lines bundled). The tldraw textarea is fine. The marginal UX improvement doesn't justify the bundle size and complexity.

**Settings panel**: Theme and font preferences are better handled at the app level (tlda app settings) than as a placeable shape. Low priority — the current defaults are good.

**Command palette**: tldraw's built-in tool palette handles the canvas-side. Fleet commands (filter chat, focus agent, open terminal) are better surfaced as toolbar buttons and shape interactions than as a text command palette. The old `/sp`, `/vsp`, `/tab` commands were compensating for dockview's panel system — tldraw's drag-to-place replaces them.

---

## Coherence Check

The five priorities above address five distinct gaps in the current system:

1. **Playback** — async review of what happened (nearly done, needs merge)
2. **Tasks** — fleet-wide task visibility (not built)
3. **Terminal** — last case requiring terminal access (spec'd, not built)
4. **Canvas capture** — making playback a true workspace replay (not started)
5. **Agent-push layout** — making the canvas a shared workspace, not just a view (not started)

Items 1-3 are completions: features that existed in the old dashboard or were explicitly designed, just not yet landed. Items 4-5 are genuinely new — they're what justifies the tldraw architecture over the old dockview dashboard. The whole point of having fleet shapes in the same canvas as the document is that agents and humans can share the spatial context. That only works if agents can write to it.
