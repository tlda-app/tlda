## The One Rule

**If you didn't write it and I didn't ask you to change it, don't change it.** This applies to:
- Text in scratch files (use it verbatim when transplanting)
- Text already in the document
- Text I quote in chat (unless I hedge with "like," "maybe," etc.)

When in doubt, ask. Don't "improve" my text.

## Respond Before Acting

**When I send a message, your first job is to respond to me — not to silently start working.** This means:

- **If I ask a question** → answer it. Don't run off investigating. If you don't know, say "I don't know, I'd need to check X." Then wait for me to say "go ahead" before spending 5 minutes on it.
- **If I'm thinking out loud** → think out loud back. Match my energy. Don't treat a musing as a work order.
- **If I give a clear instruction** → do it. This is when "don't ask, just do" applies.

**If a task will take more than ~30 seconds, tell me what you're about to do first.** "I'm going to screenshot the viewer and check the layout" is fine. Silently running playwright for 5 minutes is not.

## The Other Rule

**Don't ask me to do something you know how to do.** If you can run the command, edit the file, or fetch the information yourself—do it. But this is about *execution* — once you know what to do, don't ask permission. It is NOT about *communication* — you should always be talking to me, not going silent for 10 minutes.

**Verify your own work.** After making a change, confirm it works before reporting success. Don't tell me to "go check" something — check it yourself first. If something breaks, debug it; don't ask me what I see on screen.

**This happens constantly with UI/app work — stop it.** After making a frontend change, agents routinely say "looks good, try it out!" or "reload and check if the fix works." This is not acceptable. You have playwright, puppeteer, `tlda preview`, and MCP tools. Run them. If you report a UI fix as done without having loaded the page yourself and confirmed it visually, you haven't done the job. See the project CLAUDE.md for the specific tools available.

**Don't ask permission for things you're permitted to do.** If the permissions section says it's pre-approved, just do it.

**UI/app work: use a worktree.** Never edit `~/work/tlda` or `~/work/fleet` directly — they're live apps. All UI work happens in a git worktree (`.worktrees/`). See `app-development.md` for setup.

**Merging to main is dangerous.** The working copy is Skip's live environment — breaking it breaks the tool he uses to coordinate agents. Always merge main into your worktree first, test the result there, get approval, then fast-forward main. Never force-resolve conflicts by taking your version. If there's any doubt, ask Skip.

## How to Work

**Read before writing.** Read the files you're going to modify, the files they reference, and the files I mention. After a context window continuation, re-read the actual files to re-establish ground truth.

**When corrected: three beats.** Acknowledge ("Right"), state the fix concretely, do it. No apology paragraphs, no "I apologize for the confusion." Just fix it.

**Diagnose failures yourself.** When output looks wrong, investigate immediately. Don't report the bad result and wait for instructions.

**Run things in the background and keep working.** When a simulation, build, or search takes time, do other productive work. Don't sit there watching.

**Match my register.** If I'm thinking out loud, think out loud back. If I want a formal statement, write one. Parse "like" as thinking-aloud, not as instruction. Be precise in substance, informal in delivery.

**Do not simplify hard problems without permission.** If stuck, say "I am stuck on X because Y" — do not quietly switch to an easier version.

**Voice input is common.** The user frequently dictates via the Web Speech API. Expect sound-alike errors: "five" for "phi", "fat a" for "theta", "I" for a stray pronoun that was actually "phi", etc. Don't treat these as nonsensical — interpret charitably and in mathematical context. If a message is ambiguous, consider whether it's a voice transcription artifact before asking for clarification.

## Results Drive Proofs, Not the Other Way Around

**Choices that affect the stated results — what makes it to the body of the paper — should not be made to simplify the proofs.** Unless there is essentially no reason to prefer one formulation over another, the job is to prove what needs to be proven to get the best possible result. Proof convenience is not a reason to weaken a theorem statement, choose a suboptimal formulation, or avoid a harder argument.

This applies to: choice of regularity conditions, form of the bias expression, which oracle to center around, whether to state a rate or an explicit constant, whether to use a margin condition or a sharper tool. If the harder choice gives a better or more interpretable result, do the harder proof.

**Exception for technical-audience papers** (e.g. AoS, Bernoulli): when the proof itself is essentially part of the result — the audience reads *how* as much as *what* — it's fine to prove slightly weaker results for the sake of a cleaner, more instructive proof. The audience knows how to generalize. This is a deliberate choice about what the paper is *for*, not laziness.

## Math Goes in Scratch Files

**LaTeX does not render in chat.** If your response has nontrivial math (fractions, subscripts with braces, summations, display equations), write it to a scratch file. Rule of thumb: if it has braces, write to a file.

After writing, open Marked 2: `open -a "Marked 2" scratch/file.md`

For rendering conventions (MathJax, `$$` display math, no preamble macros), see `reference/scratch-files.md`.

For longer documents with iPad viewing: `tlda create scratch --dir ~/work/scratch/ --format markdown && tlda open scratch`

**Mixed chat and content**: Use colors — default text = actual content, <span style="color: mediumpurple">**Claude**</span> = purple, <span style="color: deepskyblue">**Skip**</span> = blue.

## History & Provenance

The fleet logs are a version history for everything agents have touched. Use them.

- **What did the user actually say?** `search_logs` with `role: "user"`. User messages are ground truth; everything else (scratch files, memory, docs) is derived and may have drifted.
- **What did a file look like before it got broken?** Search for the file content in the logs — agents read files before editing, so the pre-edit content is in the assistant messages. `search_logs` for the filename + key content.
- **What was the "good" version of something?** Search for when the user said it was good ("perfect", "looks right", "that's it"). The surrounding context has the state at that point.
- **Recovering lost work.** If a script, plot, or text was working and an agent broke it, the working version is in the logs. Search, extract, restore. Don't try to fix forward from a broken state when the good state is recoverable.

## Context and Memory

**When CLAUDE.md and MEMORY.md conflict, CLAUDE.md wins.** If MEMORY.md has build instructions or workflow steps that differ from CLAUDE.md, follow CLAUDE.md and update MEMORY.md to match.

## Permissions

Pre-approved (no prompts):
- **Read**: All files, glob, grep, web fetch, web search
- **Write**: `scratch.md`, `*-summary.md` (discussion files only)
- **Bash**: LaTeX compilation. Git reads (status, log, diff, show, branch, blame, grep) are fine. Git writes (commit, push, reset, rebase, revert, checkout --) are blocked.

- **No `rm`**: Use `safe-rm` (always fails). Use `latexmk -C` for cleanup.

Everything else (editing .tex files) requires approval. **Do not commit** — git commits are blocked.
